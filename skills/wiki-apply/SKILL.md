# wiki-apply

Surface and apply pending wiki maintenance proposals. The weekly
`dev.depasquale.wiki-maintenance` launchd agent runs `wiki-lint.py`
and feeds findings to a local 7B Ollama model, which writes proposals
to `~/projects/knowledge-vault/wiki/.lint/proposals-YYYY-MM-DD.md`
and drops a `PENDING` flag.

**A 7B local model is too small to be trusted with direct edits.**
This skill is the manual review gate — every proposal requires
explicit user approval before it touches a wiki page.

## Modes

- **`auto`** (default when invoked from SessionStart hook): apply
  every block in `proposals-auto-YYYY-MM-DD.md` without asking;
  surface a one-line summary; leave `proposals-defer-YYYY-MM-DD.md`
  alone for explicit review later.
- **`interactive`** (default when invoked manually): walk every
  block in BOTH the auto and defer files, ask `apply | skip | defer`
  per item.

Detect mode from invocation context: if the SessionStart hook injected
an "AUTO-APPLY directive" block, run in `auto` mode. Otherwise
`interactive`.

## Where the rubric lives

The auto/defer split is decided by `~/projects/vault-engine/maintenance/wiki-judge.py`,
not by this skill. The script applies the rubric in code (PyYAML
parsing, deterministic gates) and emits two files in
`~/projects/knowledge-vault/wiki/.lint/`:

- `proposals-auto-YYYY-MM-DD.md` — judge said high-confidence
- `proposals-defer-YYYY-MM-DD.md` — judge said low-confidence

In `auto` mode you trust the judge: read the auto file, apply each
block. **You should still verify each apply succeeded** (Read the
target after Edit, confirm frontmatter parses) but you do NOT
re-judge.

The judge's gates (for reference, in case you want to understand
defer reasons):
- only `update-frontmatter` adding `name|type|tags|status:evergreen`
  is unconditionally auto
- `update-frontmatter` adding `description` requires:
  length 40–120, no filler markers, target body >200 chars,
  no verbatim dup of title/name
- `mark-evergreen` only on meta/index pages
- target must appear in lint findings (anti-hallucination)
- target frontmatter must not already have a value for the field
- `type` value must match path-derived default

Anything else → defer. Never guess; if a block surprises you, treat
the judge's verdict as authoritative.

**Cap**: max 10 auto-applied proposals per session. If more, apply
first 10, defer the rest, leave PENDING for next run.

## Workflow

1. **Check staleness (per-target).**

   ```
   ~/projects/vault-engine/maintenance/wiki-pending.py check
   ```

   `PENDING` records one hash per proposal *target* (schema 2), so the
   gate fires only when a page some proposal actually edits has moved.
   Unrelated vault churn — `hot.md` rewritten at session end, a new
   entity page, `log.md` — is not drift and must not block the run.

   Exit codes:
   - `0` — every target fresh, proceed.
   - `3` — a target moved. Skip **only the proposals whose target
     appears in `.stale[]`**; the rest still apply. Say which you
     skipped and why.
   - `4` — legacy schema-1 `PENDING` (a bare 16-hex vault sha).
     Migrate with `~/projects/vault-engine/maintenance/wiki-pending.py write`, then
     proceed: proposals are re-diffed against the live target at
     apply time anyway.
   - `2` — no `PENDING`, or unreadable. Nothing to apply.

   Offer a full regenerate (`~/projects/vault-engine/maintenance/wiki-maintenance.sh`) only
   when *every* proposal is stale.

2. **List proposal files.**
   - In `auto` mode: read `proposals-auto-YYYY-MM-DD.md` only.
   - In `interactive` mode: read both `proposals-auto-*.md` AND
     `proposals-defer-*.md` for the latest date.
   - Original `proposals-YYYY-MM-DD.md` is the unsplit raw file
     (LLM output); usually you don't need it.

3. **Parse proposals.** Each block:
   ```
   ### proposal-NNN
   type: update-frontmatter | add-wikilink | remove-wikilink | merge | rename | mark-evergreen | review
   target: <path>
   finding: <type>
   rationale: <one sentence>
   action:
   ```yaml
   <change spec>
   ```
   ```

4. **For each proposal:**

   **Auto mode**:
   - Apply rubric above. If high confidence: edit immediately, verify
     frontmatter still parses, count as applied.
   - If low confidence: count as deferred.
   - Never ask the user mid-loop in auto mode. Surface the summary
     after the loop.

   **Interactive mode**:
   - Show the user: number, type, target, rationale, concrete diff
     (compute the diff yourself by reading the target file and the
     action block).
   - Ask `apply | skip | defer` via AskUserQuestion.
   - On `apply`: make the edit with `Edit`/`Write`. Verify the file
     parses (frontmatter still valid). If anything looks wrong, abort
     and report.
   - On `skip`: do nothing, mark as skipped.
   - On `defer`: leave for next session.

5. **Record outcome** in the commit subject — `git log` is the operation
   log since 2026-09-26 (`wiki/log.md` is frozen):
   ```
   wiki-apply: applied N (prop-001, prop-003), deferred K (prop-002)
   ```
   Or for interactive mode: include skipped count.

6. **Cleanup.**
   - If all proposals resolved (applied or skipped), delete that date's
     `proposals-*.md` files and `PENDING`.
   - If any deferred, leave them in place and **re-write PENDING**:
     ```
     ~/projects/vault-engine/maintenance/wiki-pending.py write
     ```
     Do this as the *last* action of the session, after your final
     vault write — not mid-session. The 2026-08-30 refresh was correct
     when taken and stale sixteen minutes later, because the session
     kept writing after it. Schema 2 largely defuses that trap (only
     the proposals' own targets are hashed), but writing last is still
     the honest order.

7. **Vault commits.** After applying, commit once with a message that
   names what was applied (e.g. `wiki-apply: applied 2, deferred 1`) and
   push. Obsidian Git is retired (2026-09-25); `wiki-autocommit.sh` only
   catches leftovers at SessionEnd, under a generic message.

## Hard rules

- **Never** apply without explicit user `y` for that specific proposal.
- **Never** trust the LLM proposal blindly: validate frontmatter syntax,
  check that wikilink targets actually exist, reject any path the model
  invented that isn't in the lint report.
- **If `wiki-pending.py check` reports a stale target**: skip the
  proposals aimed at that target and say so. Applying a proposal whose
  target moved underneath it is the one case where stale proposals
  corrupt newer state. Proposals aimed elsewhere are unaffected — do
  not block them.
- **No new files**: proposals can edit existing pages, not create new
  ones. If a proposal asks to create a stub, prompt the user explicitly.

## Files

- proposals: `~/projects/knowledge-vault/wiki/.lint/proposals-*.md`
- pending flag: `~/projects/knowledge-vault/wiki/.lint/PENDING`
  (schema 2, per-target hashes — written and verified by
  `~/projects/vault-engine/maintenance/wiki-pending.py`)
- raw lint: `~/projects/knowledge-vault/wiki/.lint/report.json`
- regenerate: `~/projects/vault-engine/maintenance/wiki-maintenance.sh`
